## The Gaming Room: Software Design Reflection

The client for this project was The Gaming Room. They wanted to expand their game, Draw It or Lose It, from Android to a web-based application that could run on multiple platforms. The application needed to support multiple games, teams, and players while making sure each had a unique name and identifier. The design also needed to consider the operating system, memory management, storage, security, and the ability to support more users as the game grows.

I think I did a good job of explaining the client's requirements and comparing the different operating systems. I was able to look at the advantages and disadvantages of each platform and explain why Linux would be the best choice for hosting the application. I also considered the costs, performance, and how the server could handle more users in the future.

Working through the design document helped me understand the importance of planning before starting development. It gave me a chance to break down the requirements and think about how the different parts of the application would work together. Having a plan makes it easier to understand what needs to be done and helps prevent problems later in development.

If I could go back and change one part of the document, I would add more detail to the system architecture section. Explaining how the server, database, and user devices would communicate would make the design easier to understand and give developers a better idea of how everything should work together.

When working through the design, I focused on what the client needed and how the application could meet those requirements. Using a Linux server and allowing users to access the game through a web browser would make it available across different operating systems without needing a separate application for each one. Considering the client's needs is important because the software needs to solve the problem it was designed for and work the way the users expect it to.

My approach to software design was to break the requirements down, compare different options, and consider the advantages and disadvantages before making a recommendation. I also looked at how memory, storage, networking, and security would affect the application. In future projects, I would continue using this approach by identifying the requirements first and planning how the different components will work together. I think taking the time to plan ahead makes development easier and helps create software that is easier to maintain and expand.
